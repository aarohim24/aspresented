# as-presented

> `"frequency": "as_presented"` — the one field in a UPI mandate that looks
> like a rate limit and isn't. It means *charge whenever presented*.

**A payment mandate says how much may be charged at once. It does not say how
many times.**

When you authorise a recurring charge — a subscription, or an AI agent
shopping on your behalf — you grant a mandate. On Razorpay's UPI rails that
mandate carries exactly four fields: a per-charge ceiling, an expiry, a
frequency label, and a type. There is no field for a total, a rate, or a place
the money is allowed to go.

So a valid mandate can be charged at its ceiling, repeatedly, until it
expires, and every individual charge is legitimate. A human would notice. An
agent that loops, retries, or reads a malicious instruction off a web page
will not, and nothing downstream objects.

This project supplies the constraints the mandate lacks, binds each charge to
the intent that justified it, and records every decision in a tamper-evident
log so a merchant can show what was authorised when a charge is disputed.

---

## What is actually missing, measured

Three rails, normalised into one envelope. Generated by
`python3 tools/gen_coverage.py`, not typed by hand:

| Constraint | razorpay (as_presented, default) | razorpay (monthly) | ap2 (open mandate) | card-on-file |
|---|---|---|---|---|
| Per-charge ceiling | **enforced** | **enforced** | declared | -- |
| Expiry | **enforced** | **enforced** | declared | **enforced** |
| Total cap | -- | -- | declared | -- |
| Charge count cap | -- | -- | declared | -- |
| Rate limit | -- | **enforced** | declared | -- |
| Spend scope | -- | -- | declared | **enforced** |
| Intent binding | -- | -- | declared | -- |

Only expiry is universal. **A total cap, a charge-count cap and a rate limit
are enforced by no network at all.** That is the gap this layer fills.

Note the shape of it: each rail is missing something a different rail has.
Razorpay gives you a ceiling but no intent binding; AP2 binds intent but sets
no ceiling; a stored card does neither. A merchant accepting agent traffic from
more than one source cannot rely on any of them, which is why the policy layer
belongs to the merchant.

## The evidence

`evidence/schema-findings.json` is the output of `probes/probe3_schema.py` against the
**live Razorpay test-mode API** on 2026-08-22.

The baseline mandate — `max_amount`, `expire_at`, `frequency:
"as_presented"`, `type: "single_block_multiple_debit"` — was accepted. Seven
attempts to add a missing constraint were each rejected by name:

```
cumulative_max_amount   BAD_REQUEST_ERROR | is/are not required and should not be sent
total_amount            BAD_REQUEST_ERROR | is/are not required and should not be sent
max_debits              BAD_REQUEST_ERROR | is/are not required and should not be sent
total_count             BAD_REQUEST_ERROR | is/are not required and should not be sent
max_debits_per_day      BAD_REQUEST_ERROR | is/are not required and should not be sent
allowed_merchants       BAD_REQUEST_ERROR | is/are not required and should not be sent
allowed_mcc             BAD_REQUEST_ERROR | is/are not required and should not be sent
```

The token object is a strict allowlist. Reproduce it in thirty seconds:

```bash
export RZP_KEY_ID=rzp_test_...
export RZP_KEY_SECRET=...
python3 probes/probe3_schema.py
```

**How strong is this claim?** It rests on three things together: the API
allowlists strictly and names the field it refuses; Razorpay's own SBMD
integration guide documents exactly those four fields and no others; and seven
independently-chosen names all missed. That is strong evidence the vocabulary
is closed. It is *not* proof that no such field exists under some name nobody
has guessed. Stated precisely: **no documented field, and none of seven
plausible undocumented ones, can express a total or a count.**

The AP2 column is mapped against the published schemas, copies of which are in
`evidence/`. It is a mapper, not a live integration.

## Limitations, stated before you find them

- **The debit endpoint is not wired.** `/v1/payments/create/recurring`
  requires account-level activation this build does not have; a fresh test
  account gets `The requested URL was not found on the server`. So charges are
  executed against a rail simulator implementing *exactly* the enforcement
  Razorpay documents — a per-charge ceiling and an expiry — and nothing more.
  Every reported number comes from that simulator, and the simulator is
  deliberately no smarter than the documented rail.
- **One adapter is wired; two are mappers.** Mandate orders are created
  against the live Razorpay API for real. AP2 and card-on-file are mappers
  verified against recorded fixtures. `Adapter.WIRED` says which, and a test
  asserts exactly one is true.
- **Intent binding here is not hardware-backed.** Real non-repudiation needs a
  device-held key. This build signs intent records server-side, which proves
  the record was not altered afterwards — not that a specific human authored
  it.
- **The gate is single-writer.** A decision reads the whole ledger and then
  appends, and nothing serialises the pair, so two concurrent charges on one
  mandate could both pass a cumulative check. Not fixed: this build is one
  process, and an in-process lock would give false confidence. Production needs
  the read and append serialised per mandate.
- **Replay is O(n) per decision.** State is derived by reading the log, which
  is correct but linear. The fix is a checkpoint derived from the chain and
  re-verifiable against it, never a free-standing counter.
- **No dispute rail accepts this evidence today.** NPCI's URCS has no field for
  a mandate scope. The evidence pack demonstrates what *should* exist; it does
  not integrate with a system that has nowhere to put it.

## Results

```
python3 tools/run_harness.py
```

Held-out split, 13 abuse classes, seed 7:

```
False-decline rate       0.00%   (0/198 honest charges refused)
Abuse recall           100.00%   (39/39 refused)
Caught by policy/rail   36/3
Value blocked           Rs 135.03
```

**Read the recall number with suspicion.** The same author wrote the abuse
generator and the checks, so every class trips the check built for it. 100%
recall demonstrates the wiring, not the difficulty of detection, and it is an
upper bound rather than a production estimate.

**The false-decline rate is the number that means something.** Of those 198
honest charges, 8 scenario families sit *exactly* on a limit -- four charges
summing to the cumulative cap to the paisa, precisely `max_charges` charges,
precisely the rate limit inside one window, a charge at the rail ceiling, a
charge at the last second before expiry, a correct retry reusing its
idempotency key, and an identical purchase one second outside the duplicate
window. Comfortable mid-range traffic would never expose an inclusive/exclusive
slip. These do, and none of them was refused.

Two abuse classes are deliberately evasive for the same reason:
`drain_by_one_paisa` exceeds the cumulative cap by a single paisa, and
`burst_one_second_early` fires one second before the rate window clears. Both
are caught.

### An attacker that never read the checks

```
python3 tools/run_attack.py
```

The harness scores traffic its author wrote, which cannot find a flaw in its
author's model of the attacker -- as it did not find the caller-controlled
clock. So there is a second instrument.

An attacker sees a `Briefing` and nothing else: the mandate's own terms, the
merchants and intents it has observed, and every refusal it has received. It
does **not** see the merchant's policy, and a test asserts that. Then the
finished ledger is judged by `invariants.check`, which states properties over
what actually settled rather than re-running the gate's own logic -- a
re-implementation reading the same request field would have agreed with the
clock bug.

```
   tempo  settled    extracted   of cap  codes reached
      0s        4      Rs 8.07     40%  6
    600s        6     Rs 18.07     90%  6
   1200s        6     Rs 18.07     90%  6
   4000s        3     Rs 11.01     55%  4
  86400s        1      Rs 1.01      5%  5

refusal codes reached: 9/9
closest approach to the cumulative cap: 90% (Rs 20.00)
NO INVARIANT VIOLATIONS AT ANY TEMPO
```

Read the two columns differently. **Extracted** is what the attacker got away
with, and a mandate is meant to be spent -- reaching 90% of the cap is the
expected outcome, not a finding. **Violations** are invariants the gate let be
broken, and any one is a defect. CI fails on any.

Three things this instrument taught its own author:

**Tempo decides which constraint binds.** At one instant the rate window is
exhausted after four charges and the cumulative cap is never reached; twenty
minutes apart puts the cap and the count under real pressure; a day apart
outlives the mandate. A single tempo under-covers, so the tool sweeps.

**`DUPLICATE_CHARGE` is hygiene, not a control.** The fingerprint is (intent,
merchant, amount), so a first version of the fuzzer sending round numbers spent
32 of 40 attempts refused as a duplicate and never reached the deeper
constraints. One paise of jitter walks past it. It catches the honest retry
storm it was built for; it does not stop an adversary.

**Two checks were unreachable.** The coverage report named `POLICY_EXPIRED` and
`INTENT_UNBOUND` as never provoked -- gaps in the attacker, not the gate. An
`unbind` strategy and a day-long tempo closed both. An unreached code is
reported either way rather than quietly dropped.

The oracle has its own integrity test, and it is the one that gives the sweep
meaning: with the cumulative check removed from the gate, the attacker must
exceed the cap and the oracle must say so. If that test ever passed trivially,
the sweep would have stopped measuring anything.

A clean sweep is not proof of correctness. It means one attacker, at five
tempos, within one budget, found nothing.

### A model attacker, on any endpoint

```bash
export GROQ_API_KEY=...            # free tier, no card
python3 tools/run_attack.py --attacker model
```

The fuzzer is systematic but bounded by strategies its author imagined. A model
given the mandate and a goal is not, which is the only way recall stops being a
tautology.

Provider-agnostic by construction: the request shape is OpenAI-compatible chat
completions, so `--base-url` and `--model` point wherever you like. Written
against raw HTTP rather than a vendor SDK, so the core package stays
dependency-free -- a project whose thesis is that rails disagree should not
hard-wire one vendor. Defaults target Groq's free tier and throttle to stay
inside 30 requests/minute.

**Model runs have no seed**, so an unrecorded finding exists only in someone's
terminal. Every exchange is written to `evidence/` -- including the prompt,
which is the evidence that the attacker was never shown the merchant's policy --
and `--attacker replay` re-issues exactly those proposals with no credentials
and no network. That is what makes a model result verifiable rather than
asserted.

Three rules the tool enforces on itself:

- **A run with no attempts reports `INCONCLUSIVE`, not clean.** Found by
  auditing: with a rejected key every call failed and the sweep still printed
  "no invariant violations". Nothing was tested, so nothing was shown, and that
  is the most misleading output this tool could produce. It now exits 2.
- **Results from different attackers are never merged.** Author-written,
  deterministic, and model-driven recall mean different things.
- **Credentials are redacted before anything is written.** Error bodies echo the
  key that failed, and transcripts get committed.

### Why the numbers are trustworthy

The harness will not print a score until two controls pass:

| Control | Expectation | Observed |
|---|---|---|
| **A** -- policy limits off | near-zero declines, collapsed recall | 0.00% declines, ~21% recall |
| **B** -- a gate that refuses everything | both saturate | 100% declines, 100% recall |

Control A is the important one. If recall were already high with no policy, the
labelled "abuse" was never abusive and the headline would be measuring
nothing. Recall collapsing from 100% to roughly a fifth shows the policy layer
is doing the work. What survives is the rail catching its own ceiling
violations plus the gate's clock-skew validation, which is input checking
rather than a merchant policy choice and so still fires.

Control B proves the metrics are wired to the decisions rather than computed
from labels.

The split is **stratified by scenario family**. A plain shuffle dropped an
entire abuse class out of the holdout during development, and the report
omitted it silently rather than scoring it.

## The console

```bash
python3 tools/serve.py      # then open http://127.0.0.1:8700
```

Standard library only -- no build step, nothing to install, works offline.
Everything on the page is computed at load from the real code: the coverage
table from the adapters, the scores from the harness, the verdicts from an
actual hash-chained ledger built by running charges through the gate.

The dispute console holds two mandates that differ in exactly one line of
policy. Adjudicating one charge from each is the whole argument:

| Charge | Mandate | Verdict |
|---|---|---|
| `A-groceries` | intent binding **off** | `UNPROVABLE` |
| `B-milk` | intent binding **on** | `AUTHORISED` |
| `B-inflated` | agent charged 500 against an intent for 450 | `UNAUTHORISED` |

`UNPROVABLE` is not a failure of the adjudicator. It is the evidence gap,
reported honestly rather than dressed up as a defence:

> This mandate did not require intent binding, so no record exists of what the
> principal asked for. The charge was within the mandate's limits, but
> authorisation cannot be demonstrated -- only permission can.

That is the position every agent purchase on today's rails is in. Turn one
field on and the same charge answers:

> A signed intent, verified from the ledger, approved up to 450 paise at
> shop-a. This charge of 450 paise conformed to it. At the time it was the
> charge numbered 1 on this mandate, bringing the total to 450 paise. The
> decision log verifies, so this record was not altered after the fact.

Adjudication reads the ledger and nothing else. Intent signatures are
re-derived from the recorded copy, and the cumulative position is recomputed
from the entries preceding the disputed charge rather than read from a running
total -- because at dispute time, nothing in memory should be trusted.

## Corrections made during the build

Recorded rather than quietly fixed, because each one narrowed a claim that had
been too broad.

**`frequency` is a rate limit after all — except under the default.** An
earlier version asserted Razorpay expressed no cadence whatsoever. False: the
fixed buckets allow one debit per billing cycle. Only `as_presented` expresses
none. The narrower statement is stronger, and a reviewer who knows the product
would have caught the old one immediately.

**AP2 expresses far more than this project first claimed.** The original
adapter modelled "IntentMandate" and "CartMandate" objects that do not exist in
the specification, and consequently missed that AP2 names a total cap
(`payment.budget`), a charge count (`agent_recurrence.max_occurrences`), a
ceiling (`amount_range`), a scope (`allowed_payees`) and key binding (`cnf`).
The claim "no format expresses a total cap" was simply wrong. What replaced it
— *declared everywhere, enforced nowhere* — is both true and a better argument.

**The gate trusted the caller's clock.** `ChargeRequest` carried an
authoritative timestamp used for rate limiting, expiry and duplicate detection.
An agent that advanced the value it reported walked through a two-per-hour
limit eight times. Server time is now authoritative, a caller-asserted
`claimed_at` is recorded and skew-checked but never acted on, and
`TestClockIsNotCallerControlled` is the regression.

That last one is worth dwelling on: **the harness could not have found it.**
The harness generates its own timestamps honestly, so the attack was outside
the space it searches. Author-written adversarial traffic cannot find a bug in
the author's model of the attacker — which is the argument for handing the job
to something that did not write the checks.

**Idempotency was backwards.** Reusing a key is what a well-behaved client does
after a timeout; refusing it turned correct retries into false declines. A
repeated key now returns the recorded decision, and `DUPLICATE_CHARGE` targets
the retry storm that *loses* its key instead.

**The drain demonstration was rigged.** It ran through a gate with its features
switched off, which is not the same as no gate. It now calls the rail directly.

## Design

The core decision is in `mandate_gate/envelope.py`: constraints are split into
what the **rail** enforces and what **policy** adds. An adapter declares its
rail's real capabilities and is forbidden from inventing others — the Razorpay
adapter raises rather than accept a `cumulative_max_amount`, mirroring the
live API, so no caller can believe a cap took effect when the rail has no such
field.

`MandateEnvelope.unenforced_by_rail` then names, at runtime, exactly which
constraints exist only because this layer supplies them. The finding is a
property of the type system rather than a claim in a document.

Refusals are actionable, which is the difference between a gate and a wall. A
bare 403 teaches an agent nothing and it retries the same call; every refusal
here names the field and the fix:

```json
{
  "code": "CUMULATIVE_EXCEEDED",
  "field": "amount",
  "detail": "2500 would exceed total cap 2000 (2000 already used)",
  "remediation": "Charge at most 0 paise."
}
```

One correction worth recording. An earlier version treated a repeated
idempotency key as an attack. That was wrong: reusing a key is exactly what a
well-behaved client does after a timeout, and refusing it turned correct
retries into false declines. A repeated key now returns the original recorded
decision. The real failure is the retry storm that *loses* its key and
resubmits the same purchase under a new one, which `DUPLICATE_CHARGE` catches
on a purchase fingerprint instead.

```
mandate_gate/
  envelope.py            normalised mandate + rail/policy split
  charge.py              intents, charge requests, actionable refusals
  gate.py                the eight policy checks
  rail.py                simulator -- documented enforcement only
  ledger.py              hash-chained, tamper-evident decision log
  adapters/
    razorpay_upi.py      wired to live test-mode API
    ap2.py               fixture-verified mapper
    card_on_file.py      fixture-verified mapper
  attack/
    base.py              what an attacker may see -- and may not
    fuzzer.py            deterministic, adaptive, no credentials
    model.py             any OpenAI-compatible endpoint, plus replay
    invariants.py        the oracle: properties over the finished ledger
    session.py           run an attacker against a real gate
  harness/
    scenarios.py         labelled traffic: honest, boundary, abusive
    runner.py            per-session execution, ledger verified after each
    metrics.py           false-decline rate first, per-class recall named
tools/gen_coverage.py    regenerates the coverage table
tools/run_harness.py     integrity preflight, then held-out score
tools/run_attack.py      adversarial sweep, judged by the invariant oracle
evidence/                live API findings
  adjudicate.py          dispute-time verdicts, from the ledger alone
tools/serve.py           local console (stdlib http.server)
  fixtures.py            canonical sample mandates, with provenance
tests/                   167 tests, stdlib only
```

The ledger is a tamper-evident local log, not a blockchain, and claims nothing
about distributed consensus. Editing or removing any entry breaks verification
of everything after it — which is the property a merchant needs: proof that
nobody rewrote history between the charge and the dispute.

## Running it

No dependencies beyond the standard library. Python 3.9 or newer -- 3.9 is the
floor because that is what a stock macOS toolchain ships.

```bash
python3 -W error::ResourceWarning -m unittest discover -s tests -t .   # 167 tests
python3 tools/run_harness.py                                           # scores
python3 tools/run_attack.py                                            # sweep
python3 tools/gen_coverage.py                                          # the table
python3 tools/serve.py                                                 # the console
```

Every number in this README is reproducible. The harness is seeded and the
split is deterministic, so the figures above are what you will see.
